# Dasii Web 헌법

## 핵심 원칙

### I. KISS (Keep It Simple, Stupid)

- 모든 코드는 가장 단순한 방법으로 구현해야 한다 (MUST)
- 당장 필요하지 않은 기능은 구현하지 않는다 (YAGNI)
- 추상화는 동일한 패턴이 3회 이상 반복될 때만 도입한다
- 한 컴포넌트/함수는 하나의 역할만 수행해야 한다 (단일 책임)
- 복잡도가 높아지는 선택은 반드시 이유를 문서화해야 한다

### II. TDD Red-Green 사이클 및 코드 리뷰

- 개발자(사용자)가 Red-Green 단계를 수행한다:
  1. **Red**: 실패하는 테스트를 먼저 작성한다
  2. **Green**: 테스트를 통과하는 최소한의 코드를 작성한다
- AI(Claude)는 Green 이후 코드 리뷰를 수행한다:
  1. **중복 로직 검출**: 동일하거나 유사한 로직이 여러 곳에 존재하는지 확인
  2. **리팩토링 제안**: 가독성, 유지보수성 개선 포인트 제시
  3. **KISS 위반 검출**: 불필요한 복잡도가 도입되었는지 확인
  4. **구조 규칙 준수 여부**: 원칙 III의 디렉토리 규칙을 따르는지 검증
- 테스트 없이 기능 코드를 먼저 작성하지 않는다 (MUST NOT)
- 리뷰 결과 리팩토링이 필요하면, 기존 테스트가 통과하는 상태를 유지하며 수행한다

### III. 프로젝트 구조 규칙 (공통 라이브러리 / 서비스 로직 분리)

- 이 프로젝트는 네이티브 앱 **Dasii**의 웹 유도 페이지이다
- 디렉토리 역할을 명확히 분리하고, 각 영역의 책임을 넘지 않는다 (MUST)

| 경로 | 역할 | 규칙 |
|---|---|---|
| `src/app/` | 라우팅 및 페이지 진입점 | 레이아웃, 메타데이터, 페이지 컴포넌트 호출만 포함. 비즈니스 로직 금지 |
| `src/components/ui/` | shadcn 기반 UI 프리미티브 | shadcn CLI로 관리. 직접 수정 최소화 |
| `src/components/commons/` | 프로젝트 공통 컴포넌트 | 2개 이상의 페이지에서 재사용되는 컴포넌트만 배치 |
| `src/components/pages/{Page}/` | 페이지별 컴포넌트 | 해당 페이지 전용 컴포넌트. `components/` 하위 폴더로 분리 |
| `src/lib/` | 공통 유틸리티 | 프레임워크 무관한 순수 함수. 사이드 이펙트 금지 |
| `src/assets/` | 정적 에셋 (아이콘, 이미지) | SVG 아이콘은 SVGR로 컴포넌트화 |
| `src/styles/` | 글로벌 스타일, 디자인 토큰 | Tailwind CSS 설정과 CSS 변수 관리 |
| `src/types/` | 공유 타입 정의 | 전역에서 사용하는 TypeScript 타입/인터페이스 |

- 서비스 로직(API 호출, 데이터 가공 등)이 필요해지면 `src/services/`를 생성하여 분리한다
- 커스텀 훅이 필요해지면 `src/hooks/`를 생성하여 분리한다
- 새 디렉토리 생성 시 반드시 이 헌법에 역할을 추가 등록한다

## 프로젝트 컨텍스트

- **프로젝트명**: Dasii Web (다시 웹)
- **목적**: 네이티브 앱 Dasii(다이어트 보조제 성분 분석 및 후기 서비스)로의 유도 웹 페이지
- **기술 스택**: Next.js 16, React 19, TypeScript, Tailwind CSS 4, shadcn/ui, Radix UI
- **대상 언어**: 한국어 (ko_KR)
- **도메인**: linkiving.com / dasii.com

## 개발 워크플로우

1. **기능 요구사항 정의**: 스펙 작성
2. **Red**: 개발자가 실패하는 테스트 작성
3. **Green**: 개발자가 테스트 통과하는 최소 구현
4. **코드 리뷰 (AI)**: Claude가 리뷰 수행
   - 중복 로직 체크
   - KISS 원칙 위반 체크
   - 디렉토리 구조 규칙 준수 체크
   - 리팩토링 가능 포인트 제시
5. **Refactor**: 리뷰 기반 리팩토링 (테스트 통과 상태 유지)
6. **완료**: 커밋

## 거버넌스

- 이 헌법은 프로젝트의 모든 개발 관행보다 우선한다
- 헌법 수정 시: 변경 사항 문서화, 버전 업데이트, 의존 템플릿 동기화 필수
- 버전 관리: MAJOR(원칙 삭제/재정의), MINOR(원칙 추가/확장), PATCH(문구 수정)
- 모든 PR/코드 리뷰는 이 헌법의 원칙 준수 여부를 검증해야 한다
